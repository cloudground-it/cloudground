2026-10-12, the same OVH VPS as [v0.2.0-rc.md](./v0.2.0-rc.md) (Ubuntu 26.04, 2 vCPU "Intel Core
Processor (Haswell, no TSX)", 4 GB; CPU parity 2.03–2.30 s through the day, 0 % steal). The
candidate is main at **6618041** (`v0.2.0-17-g6618041`): every v0.3.0 issue merged, and the
fixes this run found. It was built with `make docker-dist`, `make docker-e2e-bin` and
`make docker-upgrade-bundle`, and installed with `CLOUDGROUND_LOCAL_BUILD` on the box after
`cgctl uninstall --remove-sites --purge-packages` had taken it back to stock Ubuntu.

The first full run, on 85da91c, read **1535 passed and 8 failed**. Every failure was looked into
and fixed, and the candidate above is the build with the fixes:

- `R-6.1 installer` (1 check): since #113 the agent's unit runs `panel-agent ensure-packages` as
  an `ExecStartPre`. A sandbox that cannot be set up therefore fails the start job itself, and the
  installer printed only systemctl's message, with no unit status and no journal. The installer
  now adds the unit that is down and its journal (#119).
- `R-6.5 upgrade` (1 check): installing v0.1.0 over the box's build was refused as a downgrade,
  because `git describe`'s `v0.2.0-11-g85da91c` was read as release v0.2.0. As in #99, only a
  release tag counts now (#120).
- `blocklist` (2 checks) and `site blocking` (1 check): a block or a site rule holding the
  server's own address was accepted. The API lists the machine's addresses through netlink, which
  its unit did not allow, so the list was empty. The same cause made the webhook check, which
  refuses when it cannot tell, refuse **every** webhook, a public one included (reproduced on the
  box). The API's unit now allows `AF_NETLINK`, and `security` gained two checks (#121).
- `wordpress two-factor` (2 checks) and `malware scan` (1 check): both were the tests' own
  assumptions. The key set with wp-cli did not reach PHP-FPM's object cache, and the scanner
  names the file under the release `current` points to. The product followed its SPECs (#123).

CI also showed `TestSocketReader` (internal/agent/ops/blocklist) racing its own reads; that is
fixed in #122.

**The test harness, not the product:** twice, the full run was killed in `R-6.5 upgrade` and
started again from the beginning. The box's `needrestart` (Ubuntu's default, run after every dpkg
transaction) restarted the transient `systemd-run` unit that drove the run. The first time,
unattended-upgrades had updated libc6; the second time, it was the section's own `apt-get install
nftables`. The run above was made with needrestart told to leave the driver alone. The agent's
own helpers are transient units of the same kind, so this is filed as #125: needrestart could
restart a restore, an import or a backup partway through.

## What v0.3.0 costs, measured on the candidate

On the same box, on 85da91c. The fixes since then do not touch these paths. The details are in
each file:

- [agent-memory.md](./agent-memory.md) §4: the agent's anon peak is 63 MiB, during Quarry's 1 GB
  transfer. The cgroup reaches `MemoryHigh` only with page cache during a 2 GB restore, and that
  reclaim costs nothing (A/B). By §3's rule the values stay at 768M/1G until a second run on
  another day; that run would set 256M/342M.
- [security-scans.md](./security-scans.md): the vulnerability check costs about 3 s of wp-cli
  CPU per site per day. The malware scan peaks near 110 MiB with the reduced set (1,007 MiB with
  ClamAV's whole databases, so the 768 MB bound holds because of the reduction) and uses 115 s of
  CPU a week for the bench store. While it runs, the site's uncached pages are 11 % slower.
- [blocklist.md](./blocklist.md) §1–4: the netfilter table (with 10,000 entries too), #21's vhost
  lines and the site rules (500 networks, 50 user agents, CN + RU) are within noise on cached
  traffic. US alone is 252,915 prefixes and adds 50 MiB PSS to nginx. A 10,000-entry apply takes
  0.1 s. A guessing run against sshd costs the agent 0.13 % of one core. On the first country rule
  of the day, DB-IP's download timed out after its two minutes; the panel answered 503 and kept
  the site as it was, and the download succeeded seven minutes later.
